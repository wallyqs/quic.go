NQUIC — QUIC without TLS,
for NATS

A QUIC profile that keeps the entire transport — streams, flow control, loss recovery, migration — but removes the mandatory TLS 1.3 handshake and X.509 certificates. Built as a single alternative CryptoSetup inside quic-go.

01 Why decouple QUIC from TLS?

QUIC (RFC 9000) mandates TLS 1.3 (RFC 9001): every connection runs a TLS handshake and derives its packet-protection keys from the TLS key schedule. That coupling drags X.509 certificates and a PKI into every deployment.

NATS already has its own security model — nkeys, JWTs, tokens — and is frequently run inside a trusted boundary (a supercluster in a VPC or service mesh). There, certificate machinery is pure operational overhead, yet QUIC's transport features remain valuable. NQUIC keeps the transport and replaces only key establishment.

Figure 1. Only the top two layers change. The transport — the hard, valuable part — is untouched.

02 The seam: one interface

quic-go hides all of its TLS coupling behind a single interface, handshake.CryptoSetup. The connection run-loop only ever talks to that interface; packet protection, HKDF, the CRYPTO-frame plumbing and transport-parameter handling are already TLS-agnostic.

Figure 2. NQUIC is a sibling implementation of the same interface — everything above the bar is reused.
The Initial encryption level already derives its keys deterministically from the Destination Connection ID (RFC 9001 §5.2) and never needed TLS — so NQUIC reuses the standard Initial AEAD to protect the transport-parameter exchange.

03 Encryption levels: what each one uses

QUIC has four key "levels". NQUIC keeps Initial exactly as standard QUIC, uses a trivial null AEAD for Handshake and 1-RTT, and never does a key exchange.

Figure 3. Initial is shared with standard QUIC; Handshake & 1-RTT become the null AEAD; 0-RTT is unused.

04 The handshake, step by step

There's no key exchange to perform — the only job is to carry QUIC transport parameters and to drive the connection's key-drop / confirmation machinery in the same order TLS would.

Figure 4. The Handshake "finished" round trip is the crux: it ensures the server only completes after its Initial reply was sent, so it never drops Initial keys before the client has the server's parameters.
The bug this avoids. A naive one-round-trip design makes the server complete (and drop its Initial keys) while still processing the client's Initial — before its reply goes out. The client then waits forever. The extra Handshake flight mirrors TLS ordering and fixes it.

05 The null AEAD & the 16-byte tag

"Null" means no encryption and no authentication — payload is copied verbatim. But it can't be zero overhead, because of how QUIC protects packet headers.

Header protection samples 16 bytes, 4 into the packet number.
The null AEAD appends 16 zero bytes so small packets survive.
Why it matters in practice. Real AEADs satisfy the size requirement for free via their authentication tag. A truly zero-overhead AEAD made tiny NQUIC packets — ACKs and the "finished" — fall below the minimum, so the peer dropped them and the handshake stalled. The dummy tag is the fix.

07 NATS pub/sub over NQUIC

The example in example/nats-nquic/ runs a miniature NATS broker and two clients — all over NQUIC, no TLS, no certificates — speaking a real subset of the NATS client protocol.

Figure 7. Publisher → broker → subscriber, the classic NATS path, carried entirely over NQUIC.
# go run ./example/nats-nquic/
broker listening on 127.0.0.1:XXXXX (NQUIC: no TLS, no certs)
INFO {"server_name":"nquic-demo","proto":1}
subscriber: SUB nats.demo
INFO {"server_name":"nquic-demo","proto":1}
publisher: PUB nats.demo "hello over NQUIC 🚀"
✅ subscriber received on "nats.demo": hello over NQUIC 🚀
Server speaks first. In NATS the server greets with INFO, but a server-accepted QUIC stream only materializes once the client writes. So the broker opens the stream and the client accepts it — the one place NATS semantics are mapped onto QUIC stream mechanics.

08 Using it

The only NQUIC-specific code is handing quic.NQUICConfig() to Listen and Dial. Everything else is ordinary quic-go.

import "github.com/quic-go/quic-go"

// Server — no certificate, no TLS handshake.
ln, _   := tr.Listen(quic.NQUICConfig(), nil)

// Client — dial the same TLS-free profile.
conn, _ := tr.Dial(ctx, addr, quic.NQUICConfig(), nil)

// From here on, identical to any quic-go program.
str, _  := conn.OpenStreamSync(ctx)
str.Write([]byte("hello"))

Under the hood, NQUICConfig() returns a certificate-less tls.Config whose NextProtos contains the sentinel ALPN "nquic-null/v1". When the connection constructors see it, they route to nquicSetup instead of the TLS crypto setup — the tls.Config is only a carrier for the toggle.

09 Security model & limitations

Cleartext. The null profile provides no confidentiality and no authentication at the transport layer. Use it only on fully trusted networks (e.g. a NATS supercluster inside a VPC or service mesh) where NATS itself handles authentication via nkeys / JWT / tokens.
  • Next step — encrypted, still cert-free. An ephemeral-ECDH profile (X25519 in the Initial exchange → HKDF → a real AEAD) would keep confidentiality and forward secrecy while still dropping certificates. It slots into the same CryptoSetup seam.
  • Opt-in ergonomics. A first-class Config option (e.g. EnableNQUIC) would be cleaner than the ALPN sentinel; the sentinel was chosen to keep the prototype's blast radius small.
  • Not implemented in the null profile: 0-RTT, session resumption, key update.
